# Template literal error codes

Active guidance for the testing-and-debugging skill. Use it when TypeScript code
reports an error. Source: Matt Pocock, "Template literal types for error codes
are awesome" (https://www.youtube.com/shorts/zOseJFD447U). This is the
error-reporting pattern from that short.

## The pattern

Features and error types are separate unions. A template literal type combines
them with a colon. `reportError` takes only that combined code, then reports it
to the server. The file on screen is `template-literal-error-codes.ts`.

```ts
export type Feature =
  | "auth"
  | "payments"
  | "notifications";

export type ErrorType =
  | "too-many-requests"
  | "invalid-credentials"
  | "user-not-found"
  | "payment-failed"
  | "notification-failure"
  | "unknown";

export type ErrorCode = `${Feature}:${ErrorType}`;

const reportError = (e: ErrorCode) => {
  // ...report this to the server
};

reportError("");
```

The type frame crops the first `Feature` member. The narration lists that
feature with payments and notifications, and the autocomplete prefix is `auth:`.
The error-type members and the `` `${Feature}:${ErrorType}` `` form are visible
in the type frame. `reportError("")` is underlined because `""` is not an
`ErrorCode`.

## What autocomplete shows

Inside `reportError("")`, the editor offers the cross product, including:

- `auth:invalid-credentials`
- `auth:notification-failure`
- `auth:payment-failed`
- `auth:too-many-requests`
- `auth:unknown`
- `auth:user-not-found`
- `notifications:invalid-credentials`
- `notifications:notification-failure`
- `notifications:payment-failed`

Keep the full cross product, including pairs such as `auth:payment-failed`.

## When the set changes

Add the new error type to `ErrorType`. It becomes reportable on every feature
through the same template literal. Do not hand-maintain a second list of pairs.

When a test or a diagnosis observes a reported error, expect one of these
codes. A free string is outside the type the short uses.
