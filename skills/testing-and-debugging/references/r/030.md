# Mutation testing

Active guidance for the testing-and-debugging skill. Use it when a passing suite's
quality is in doubt. Source: Matt Pocock, "Mutation testing is AWESOME"
(https://www.youtube.com/shorts/djSbndoByr8).

## When to run it

A passing suite still needs a check that it would notice a real mistake. Run
mutation testing when that doubt matters, especially for tests an agent wrote.
Use the project's mutation tool when it has one. The TypeScript example in the
short is Stryker.js. Other languages have their own tools. Leave the mutator
out of an unrelated low-impact edit.

## What it does

The tool edits the source under test, then reruns the tests. The mutation
described in the short replaces a JavaScript string with an empty string. The
report on screen is a Stryker view of string literals in `SAFE_LINK_PROTOCOLS`
and `COMMENT_LANGS`, with each literal marked and a summary of:

- Killed (35)
- Survived (31)
- NoCoverage (4)

Those counts belong to that example report.

## How to read a mutant

- **Killed.** The tests failed on that mutation. The suite caught that change.
- **Survived.** The tests still passed. That mutant still needs to be killed.
- **No coverage.** The tests never executed the mutation. It is not evidence
  that the behavior is tested.

## How to kill a survivor

Add or tighten a test that fails while the mutation is present and passes on
the original source. The expected result is an independently known value, so
the test catches a potential bug. Leave production behavior as it is unless a
separate failing case shows that behavior is wrong. The mutator owns the edited
copy; killing a mutant means the suite rejects that edit.

Afterward, report the killed, survived, and no-coverage results, and which
survivors the new or tightened tests killed. A suite with survivors that the
tests actually reached is not yet rigorous.
